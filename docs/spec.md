# Specification revisions

Which OpenTravel publications each version of this schema was generated from,
and what changed in the output when the pin moved.

## One upstream, two publications read

coversa reads two upstreams, each its own repository. Here everything comes
from one:
[OpenTravel/OpenTravel-Specifications](https://github.com/OpenTravel/OpenTravel-Specifications),
OpenTravel's own archive of every publication since 2001A. It is a submodule
at `modules/opentravel`, which holds every upstream this repository reads and
nothing it writes. Two publications inside it are read:

| Read | Path in the checkout | Format | What it contributes |
| --- | --- | --- | --- |
| message suite 2017B | `OTA1.0/OTA2017B/OpenTravel_2017B_XML/` | XSD | every message, type, attribute, facet and closed enumeration |
| code list 2024-09-04 | `CodeLists/OTA_CodeLists_2024_09_04/OpenTravel_CodeList_2024_9_4.xlsm` | Excel workbook | the code tables an `OTA_CodeType` value is drawn from |

And one is consulted but not generated from: the OTA 2.0 2020A object suite,
`OTA2.0/OTA2.0_2020A_ObjectSuite/`. See `decisions.md` for why.

The two are **pinned separately inside one commit**. A code list is
republished far more often than a message suite -- 2016, 2019, 2024 against a
last 1.0 suite of 2017B -- so moving to a newer code list without touching the
suite is the bump this repository will see most.

`sync/spec.yaml` will read:

```yaml
repository: https://github.com/OpenTravel/OpenTravel-Specifications
commit: 28dcc880acf2d22a8a5e93d20174971080b6846c
version: 2024-11-26
suite: OTA1.0/OTA2017B/OpenTravel_2017B_XML
suite_label: 2017B
codelist: CodeLists/OTA_CodeLists_2024_09_04/OpenTravel_CodeList_2024_9_4.xlsm
codelist_label: 2024-09-04
```

The **version is the commit's date**, the way MCP versions its specification,
because the repository has no tags and a number invented here would mean
nothing. The two labels are OpenTravel's own names for its publications, and
they are what a reader recognises. All three go into every banner:

```proto
// Generated by sync from the OpenTravel 2017B XML message suite and
// code list 2024-09-04, read from OpenTravel-Specifications at
// revision 2024-11-26 (28dcc88).
// DO NOT EDIT.
```

## Bumping the pin

A pin is not a version this repository chooses; it records what was read.

```sh
git -C modules/opentravel pull   # 1. move the checkout
$EDITOR sync/spec.yaml           # 2. commit, version, publication paths
just sync                        # 3. regenerate every proto and README
just ci                          # 4. every gate
```

Then record what moved in the history table above -- new resources, renamed
fields, anything a consumer would have to react to.

`just spec` checks the pin against the checkout: the commit is the one checked
out, the version is that commit's date, the tree is clean, and both
publication paths exist. Without it a stale pin stamps a revision into every
banner that the files were never generated from.

## What a bump can break

A bump is a **breaking-change review**, not a routine update. `buf breaking`
catches a removed or renumbered field. These it cannot see, and `just survey`
or the build reports each:

- **A new message.** A newer suite adds a message the `methods` table does not
  name. That is a build error (rule 7): map it or mark it not taken.
- **New AIP collisions.** A new attribute may trip a rule no existing field
  does. The survey lists every trap; resolve it in `catalog.FieldRenames`, or
  `catalog.AcceptedTraps` with the reason, and add a row to the catalogue in
  [`conventions.md`](conventions.md).
- **A new XSD construct.** The parser accepts only what the pinned suite uses
  (rule 15). A construct it has not seen is an error, not a skipped type.
- **A changed code table.** A code list bump changes no field, only what a
  code may mean. The survey reports every table added, removed or renamed,
  and a citation the workbook no longer resolves is an error.
- **A stale rename.** An entry keyed by a path the new suite no longer has
  resolves nothing. `model.CheckCatalogue` makes that a build error naming
  each one.
