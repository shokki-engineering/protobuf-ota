# Resources and methods

Which OTA types become resources, where they sit, and which AIP method each
OTA message becomes. All three tables are code in `sync/internal/model` --
`resources*.go`, `methods.go`, `customs.go` -- and are the authority; this
page renders them. `protobuf/opentravel/README.md`, generated by `just docs`,
lists every package and RPC as emitted.

An id marked **server** is assigned by the server: the OTA type has no code
that identifies it, or (for `StatisticReport`) only a composite one. Where OTA
carries its own `@ID`, it is kept as `ota_uid` (docs/conventions.md rule
10).

Each daily resource carves its `StatusApplicationControl`: the range, weekday
mask, room type and rate plan it names are the resource's name, not a field.
A carve-out written `Group/*` -- `HotelReferenceGroup/*` -- removes every
attribute that group contributes: a child resource's name already says which
hotel it belongs to.

The resource is `StatisticReport`, not `Statistic`: AIP-140 shortens the
word `statistics` to `stats`, so a `Statistic` resource's plural and its
list field could never agree.

Events, event reports and RFPs sit at the root: each is addressed to several
hotels at once (an event's `Sites`), so no one hotel is its parent.

A service is named by the plural: `RatePlans`. Where the plural is the
singular -- `AreaInfo`, `AffiliationInfo`, `Multimedia` -- a service and a
message of one package cannot share the name, and the service is
`AreaInfoService`, `AffiliationInfoService`, `MultimediaService`.

`RoomType` is designed as **one resource drawn from two OTA types**; today
it reads only the descriptive `GuestRoom`, and the merge below is not yet
implemented. OTA describes a room
type in `FacilityInfo/GuestRooms/GuestRoom` and sells it as a
`SellableProduct` carrying a `GuestRoom` and an `@InvTypeCode` -- the code
every rate, restriction and inventory count then cites. OTA never says the
descriptive `@Code` and the sold `@InvTypeCode` are the same code; every
implementation surveyed treats them so, and the merge makes it a rule. Two
resources would put one room type at two names and leave every ARI message
to guess which it meant. Where both OTA types carry the same fact
(`MaxOccupancy`, say), `Merge.Drop` on the resource drops the second; an
unresolved overlap is a build error. At this revision there is none: the
sold side adds its inventory codes, sale period and a `guest_room` message. A
`SellableProduct` that is not a room carries a meeting room or a block, both
resources already, so it needs no resource of its own.

A **daily** resource is a collection whose ids are composed from its axes and
whose writes arrive as AIP-234 `BatchUpdate` -- rule 7, and
`decisions.md`. It still has the full standard method set.

## Methods

Every message in scope -- each `OTA_Hotel*RQ`, and `OTA_CancelRQ`,
`OTA_ReadRQ`, `OTA_DeleteRQ`, `OTA_Profile*RQ` -- and the RPCs that do its
job, from `methods.go`. `model.checkMethods` fails the build on a message in
scope with no row, a row for a message the suite lacks, or an RPC no package
declares. `Notif` messages push state the sender already holds, so they map
to the methods of the request they mirror, with the id supplied by the
caller: the receiving system implements the service.

`OTA_ResRetrieveRS` is `ListReservationsResponse`. Every collection also has
the standard methods no OTA message asks for -- `Delete` and `Undelete` on a
reservation are a purge and its reversal, distinct from cancelling it.

### Custom and batch methods

From `customs.go`. A custom request carries `name` (on one) or `parent` (on
a collection with one), then the OTA request's content less its envelope --
`POS`, `Success`, `Warnings`, `Errors`, `TPA_Extensions`, `UniqueID`,
`MessageID` and `OTA_PayloadStdAttributes`. A request and its response share
one file in `v1/`, named for the method. Each method signature names every
required request field (client-libraries AIP-4232).

| RPC | Kind | URI suffix | Request carries | Returns |
| --- | --- | --- | --- | --- |
| `Hotel.BatchGetHotels` | batch get, AIP-231 | `:batchGet` | `names` | the Hotel resources |
| `Hotel.SearchHotels` | custom, on the collection, paginated | `:search` | `OTA_HotelSearchRQ` | `OTA_HotelSearchRS`, less its envelope |
| `Hotel.SearchAvailability` | custom, on the collection, paginated | `:searchAvailability` | `OTA_HotelAvailRQ` | `OTA_HotelAvailRS`, less its envelope |
| `Reservation.CancelReservation` | custom, on one | `:cancel` | `OTA_CancelRQ` | the Reservation |
| `Reservation.QuoteReservation` | custom, on the collection | `:quote` | the reservation to price | `QuoteReservationResponse` holding the Reservation |
| `Reservation.HoldReservation` | custom, on one | `:hold` | -- | the Reservation |
| `Reservation.CommitReservation` | custom, on one | `:commit` | -- | the Reservation |
| `Reservation.IgnoreReservation` | custom, on one | `:ignore` | -- | the Reservation |
| `Reservation.ImportReservations` | custom, on the collection | `:import` | `OTA_HotelRoomListRQ` | the Reservation resources |
| `Inventory.BatchUpdateInventories` | batch update, AIP-234 | `:batchUpdate` | `requests` | the Inventory resources |
| `Inventory.AdjustInventories` | custom, on the collection | `:adjust` | `OTA_HotelInvAdjustRQ` | the Inventory resources |
| `Inventory.SyncInventories` | custom, on the collection | `:sync` | `OTA_HotelInvSyncRQ` | the Inventory resources |
| `Rate.BatchUpdateRates` | batch update, AIP-234 | `:batchUpdate` | `requests` | the Rate resources |
| `Restriction.BatchUpdateRestrictions` | batch update, AIP-234 | `:batchUpdate` | `requests` | the Restriction resources |
| `BookingRule.BatchUpdateBookingRules` | batch update, AIP-234 | `:batchUpdate` | `requests` | the BookingRule resources |
| `Summary.BatchUpdateSummaries` | batch update, AIP-234 | `:batchUpdate` | `requests` | the Summary resources |
| `Profile.MergeProfiles` | custom, on the collection | `:merge` | `OTA_ProfileMergeRQ` | the Profile |

The two searches are paginated (AIP-158): `page_size` and `page_token` on the
request, `next_page_token` on the response, and the paged field --
`properties`, `hotel_stays` -- first and numbered 1. `QuoteReservation` is
collection-level, so it returns a response message, not the resource
(AIP-136). The room list was first designed as `ImportRoomList` on an
inventory block; AIP-136 wants an RPC's noun to match its URI, and the list
books reservations, so it is `ImportReservations` on the hotel's
reservations, naming the block in its body.

## Domains

| Domain | Holds | Why one area |
| --- | --- | --- |
| `property` | what a hotel *is*: rooms, venues, policies, media, contacts | OTA's descriptive-content messages |
| `revenue` | what it *sells*, and when and for how much | OTA's ARI (availability, rates, inventory) messages |
| `booking` | what a guest *bought* | reservations and the stays they become |
| `sales` | group and event business | blocks, events, RFPs |
| `finance` | money owed to third parties | commissions |
| `reporting` | what happened, after the fact | statistics |

## Open

- **Composed ids of the daily resources** -- the separator between room type
  and day, and how a message that applies to *all* room types
  (`@AllInvCode`) maps onto ids that name one. The patterns are fixed; the id
  format inside them is not.
- `OTA_HotelInvAdjustRQ` and `OTA_HotelInvSyncRQ` are undocumented in the
  suite and structurally identical; their mapping is from their shape.
